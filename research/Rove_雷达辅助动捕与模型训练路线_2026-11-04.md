# Rove：雷达辅助动捕与模型训练路线

日期：2026-11-04  
适用范围：网页端单摄像头动捕、可驱动数字人、后续可选毫米波雷达融合。  
术语说明：以下把“Mashi / Tribal”按 Meshy / Tripo 理解。

## 执行结论

1. **目前不要先买雷达来解决角色模型、表情或手指穿插。** 雷达测量空间反射点、距离和径向速度；它不能提供脸部网格、衣服边界、手指纹理，也不能代替角色骨骼与蒙皮。先把摄像头到角色的观测、重定向、关节约束、遮挡回退做好。
2. **若要做雷达原型，优先评估 TI IWR6843ISK-ODS。** 它是 60–64 GHz、3TX/4RX，水平和垂直视场均为 120°，适合近距离室内人体活动的第一轮验证；普通 IWR6843ISK 的垂直视场约 30°，桌面全身捕捉不如 ODS 视场合适。TI 页面确认两者可通过 USB 访问点云；要采集原始 ADC 数据开展自有训练，还需评估 DCA1000EVM，开发调试可加 MMWAVEICBOOST。[TI ODS 产品页](https://www.ti.com/product/IWR6843ISK-ODS)，[TI 标准 ISK 产品页](https://www.ti.com/tool/IWR6843ISK)
3. **Rove 的模型训练必须分成三类问题，不能把“喂很多 GLB”当成一个万能训练集。** 资产生成、动作估计、跨传感器融合需要不同的输入、标签、损失函数和评测。
4. **短期不用自训深度模型。** 使用已有的 MediaPipe 姿态、手部世界坐标和面部 blendshape 系数；在其后做时序滤波、可信度控制、人体关节范围约束、IK 和接触/穿插惩罚。积累同步数据后，再训练一个摄像头—雷达融合模型。

## 1. Meshy / Tripo 与 Rove 的任务边界

Meshy 和 Tripo 这类服务主要解决文本或图像到静态 3D 资产的生成。Meshy 文档公开了 Text-to-3D、Image-to-3D、纹理和动画等 API，但没有公开其完整模型权重或网络训练方案；Meshy 对训练数据的说明提到授权/购买的模型数据。不能把它的未公开内部训练逻辑当作可复现方法。[Meshy API 文档](https://docs.meshy.ai/en)，[Meshy 训练数据说明](https://help.meshy.ai/en/articles/15724182-is-meshy-safe-and-private-data-and-training-faq)

TripoSR 是另一条可复现的路线：开源实现采用单图快速前馈式 3D 重建，技术报告描述了 LRM 风格的 Transformer / triplane 表示，并使用经筛选的 Objaverse 数据训练。它可做**静态几何起点**，不会自动给出可信的人体骨架、权重、手指关节、面部 ARKit 形态键或实时动捕能力。[TripoSR 论文](https://arxiv.org/abs/2403.02151)，[官方代码](https://github.com/VAST-AI-Research/TripoSR)，[Stability AI 技术说明](https://stability.ai/news-updates/triposr-3d-generation)

因此，Rove 可以借鉴“用大规模授权 3D 资产训练生成器”的方向，但需要单独建立人物资产管线：清洗拓扑和单位、统一骨架、标注蒙皮/面部键、做授权审计、生成多视角渲染和质量过滤。没有这些结构化标注，只有一堆 GLB 文件并不能训练出能实时动捕的模型。

## 2. Rove 的三条训练线

| 训练线 | 模型输入 → 输出 | 必要数据 / 标签 | 近期推荐 |
|---|---|---|---|
| **A. 角色资产生成** | 正面/多视角照片或文字 → 网格、材质、人体比例、骨架、蒙皮、面部键 | 具有授权的 3D 人体/扫描、网格、标准化骨架、蒙皮权重、表情形态键；每个资产需要多视角渲染与元数据 | 先用 TripoSR / Tripo 做单图静态网格原型，再用 Blender 检查、重拓扑、绑骨；训练不进入实时摄像头回路 |
| **B. 摄像头动作估计** | RGB 视频 → 2D/3D 身体、手、面部系数或 SMPL-X 参数 | 同步图像与 mocap/SMPL-X ground truth；覆盖坐姿、衣物、裙装、遮挡、不同身材/肤色/机位 | 先用 MediaPipe Tasks；姿态先验参考 AMASS，手部采用 InterHand2.6M / RenderIH 思路，脸用能匹配 52 个 ARKit 键的模型 |
| **C. 相机—雷达融合** | RGB 特征/关键点 + FMCW 点云/速度 → 可信度加权的 3D 骨架 | 同一时钟下的 RGB、雷达原始或点云、外参、人体 3D 骨架标注；覆盖自遮挡、低光、衣物遮挡、动作方向 | 先用雷达提供人体中心、距离、径向速度和相机低置信度关节的深度先验；再比较后融合与中间层融合 |

这三线最终在一个**角色求解器**汇合：把预测关节拟合到目标角色骨架时，最小化重投影误差、骨长变化、关节越界、时间抖动、足底滑动、手部穿插和躯干碰撞。该求解器是实时 IK / 约束优化层，不是逐帧重新训练深度网络。

## 3. 没有雷达能不能训练？可以，但训练目标要说清楚

可以训练图像到角色资产、单目姿态估计、手/脸追踪或动作先验，且现有研究已经采用纯视觉或 mocap 数据。但**单目视频的绝对深度有歧义**；只用渲染模型训练，仍然会有合成到真实差距。若想改善遮挡、人物到摄像头距离、身体朝向和相机不可见时的运动，雷达能提供额外观测与深度/速度线索。

训练动作模型不能只收集姿势截图。至少需要连续片段和可对齐的 3D 骨架/SMPL-X 参数。AMASS 将多个 marker-based mocap 数据集统一到 SMPL 表示，可作为动作先验和合成训练起点；SMPL-X 把身体、手和表情放在一个表达模型内。[AMASS](https://arxiv.org/abs/1904.03278)，[SMPL-X](https://arxiv.org/abs/1904.05866)

手部需要专项数据与先验。InterHand2.6M 收录约 259 万张单手/双手交互图像与 3D 关节标注；RenderIH 是互相遮挡手部的大规模合成数据方向。它们适合训练或评测手部 3D 估计，不是把识别网络直接“嫁接”到现有手指骨上就能自动解决穿模；仍需正确手掌坐标系、骨长保持、关节角限位和手掌/胸廓碰撞处理。[InterHand2.6M](https://mks0601.github.io/InterHand2.6M/)，[RenderIH](https://adwardlee.github.io/view_renderih/)

面部同理：MediaPipe Face Landmarker 可以输出 blendshape 系数，但角色模型必须有相匹配的 morph targets / VRM expressions 才能让脸部网格变形。当前内置 Innerscene 角色没有面部 morph targets，所以 UI 数值只能表示“检测到的面部信号”，不能说成模型表情已映射。应采购或生成明确带 ARKit 52 / VRM expression 的模型，并在导入时显示映射覆盖率。

### 已筛选的模型候选：Ara 3D Gen

[Ara 3D Gen](https://github.com/olatunde85/3d-gen) 是目前和 Rove 目标较接近的开源生成器：项目说明使用 CC0 MakeHuman 资产，支持写实人物、Mixamo 命名骨架；其脸部文档说明 GLB 可导出 20 个表情形态键和 14 个语音 viseme，含牙齿/舌头，脸部形态键采用一部分 ARKit 命名；代码 MIT，角色数据 CC0。[项目 README 与许可](https://github.com/olatunde85/3d-gen#licensing) · [Face 文档](https://github.com/olatunde85/3d-gen/blob/main/docs/faces.md) · [Rig 文档](https://github.com/olatunde85/3d-gen/blob/main/docs/rigging.md)

它更适合先生成 Rove 的**原型测试角色**，而不是直接替换当前人物：需要 Node 20+、Git，首次设置约下载 420 MB 的 MakeHuman 数据并生成约 85 MB 公共资产；当前模型不是完整 ARKit 52 键。其 Game rig 为 65 骨 Mixamo 命名骨架，Full rig 是 163 骨（含脸），因此要选包含手指的 Game 或 Full rig，不能选没有手指的 Lite rig。建议先用女性 preset 导出一个 rigged GLB，检查 morph 名称、蒙皮、指骨和 GLB 可用性；若满足，再接入 Rove 的 FaceLandmarker。此模型生成器本轮尚未克隆/运行，未把未经检查的模型塞进网页。

## 4. 雷达能补什么、不能补什么

**能补**：人物距离/相对位置、部分 3D 深度与径向速度、低光照鲁棒性、视觉关节短时遮挡时的运动先验、相机视场外仍可探测的存在感。研究数据已经验证相机/雷达同步采集、雷达 3D 姿态学习与跨模态监督可行；HuPR 使用同步视觉与 mmWave 数据，mRI 同时包含 mmWave、RGB-D 与惯性传感器，mmFree-Pose 则以惯性动捕作为雷达骨架标注来源。[HuPR WACV 2023](https://openaccess.thecvf.com/content/WACV2023/papers/Lee_HuPR_A_Benchmark_for_Human_Pose_Estimation_Using_Millimeter_Wave_Radar_WACV_2023_paper.pdf)，[mRI 数据集](https://arxiv.org/abs/2210.08394)，[mmFree-Pose 2025](https://doi.org/10.3390/bioengineering12080891)

**不能补**：表情、面部肌肉形变、手指精细关节角、服装/裙摆轮廓、照片纹理和写实人物网格。单颗商用雷达点云较稀疏，也不等同于研究级高分辨率雷达阵列。2026 年 mmWave-DensePose 工作使用四芯片级联系统，报告约 1.30° 方位和 2.24° 俯仰角分辨率、每帧平均 164 个有效人体点及 4.08 cm 平均定位误差；这与买一块普通 3TX/4RX EVM 不是同等硬件条件。[mmWave-DensePose 论文与数据](https://seu-rise.github.io/mmWave-DensePose/)

相机与雷达融合也不是总能提高：观测需时间同步和空间外参标定；不同方向动作会改变雷达回波；点云上的人体部位不一定可分。MVDoppler-Pose 等研究指出雷达动作估计受运动方向与遮挡影响；融合应按关节置信度动态选模态，不能简单把点云和视频拼接起来。[MVDoppler-Pose CVPR 2025](https://openaccess.thecvf.com/content/CVPR2025/papers/Choi_MVDoppler-Pose_Multi-Modal_Multi-View_mmWave_Sensing_for_Long-Distance_Self-Occluded_Human_Walking_CVPR_2025_paper.pdf)

## 5. 雷达采购建议

### 原型阶段：先借/租，再决定购买

若 Rove 当前目标是室内摄像头角色动捕，建议先不买雷达。先用公开多模态数据集检查“视觉低置信度时雷达是否能实际降低 3D 关节误差”，并修复当前相机姿态、手指映射和脚底接触。若实验表明价值明确，再借一块或买一块 ODS EVM 做一人、单房间、0.8–3 m 范围的验证。

### 首块板：TI IWR6843ISK-ODS

- 优点：60–64 GHz、3 发 4 收、120° × 120° 视场；比窄垂直视场的标准 ISK 更适合桌面近距离测完整人体；TI SDK 与公开研究较多。
- 先用板载 demo 的点云输出做人体距离/中心/速度/遮挡可靠性实验。
- 如果目标是**训练自己的点云网络**，再采购/借用 DCA1000EVM 采原始 ADC；同步开发调试可用 MMWAVEICBOOST。采购前核实板卡互连、SDK/固件版本和本机 Windows 驱动，避免只买到无法录原始数据的配置。
- TI 当前产品页没有公开稳定的零售价格（要求登录或询价），因此不写过期报价；按中国本地渠道向 TI 授权经销商询价，并将板卡、数据采集、支架/供电和开发时间一起计入预算。

### 为什么不是直接上“高精度训练雷达”

高分辨率 3D 姿态工作通常依赖多芯片级联、校准阵列和大量同步 mocap 标注。仅为验证 Rove 的穿模或裙装问题而购买研究级阵列成本高，且雷达对裙装造成的语义歧义不一定比摄像头分割更好。先验证一个明确假设：**摄像头低置信度时，雷达能否显著改善髋、膝、踝的 3D 位置和脚底接触判断**。若这个指标没有改善，雷达不会解决本项目当前主要痛点。

## 6. 推荐训练实施顺序

### 阶段 0：零硬件训练基线（现在）

1. 保留 MediaPipe Pose / Hand / Face 作为预训练观测模型；不要在每帧反向传播或在线改权重。
2. 将关节角和骨长约束写进 retarget / IK：肘膝只允许合理弯曲方向；缺失点冻结对应骨段；置信度低时回退到短时预测与中立姿势。
3. 手使用 HandLandmarker 的 world landmarks 估掌面坐标系，再将相对姿态重定向到手指骨；保持目标骨长，限制 MCP/PIP/DIP 角度；手腕在胸腹/骨盆碰撞体前方时加软碰撞约束。
4. 腿使用髋—膝—踝连续链而不是由裙摆/单个轮廓猜腿；建立左右脚接触状态，站立脚锁在地面，只有检测到脚抬起才解除锁定。
5. 面部模型必须配有 morph targets / ARKit 52 或 VRM expressions；导入界面检查各 expression 映射，不存在的通道不显示为“已映射”。

### 阶段 1：建立 Rove 专有标注集

- 每条序列同步保存原始视频帧时间戳、MediaPipe 2D/3D 关键点与置信度、手部 21 点和 world landmarks、面部 blendshapes、模型目标骨骼旋转、用户选择的镜像状态。
- 被试动作覆盖：正面/侧面、坐/站/弯膝、抬脚、手置胸前、抱臂、手指张合、遮挡、裙装/宽松衣物、不同光线、摄像头高度/距离。
- 若要 3D 训练标签，用可穿戴 IMU/Vicon/光学 mocap 做采集标注；用户 webcam 输出本身不能同时充当 ground truth。
- 采集用途、保存时长、删除机制和授权分开征求同意。只保存匿名骨架特征时，仍要按敏感生物行为数据管理。

### 阶段 2：先训练局部模块，不端到端重造

1. **时序稳定器**：预测关节状态/置信度，使用短窗口时序模型或滤波器；评测 jitter、延迟和急停。
2. **视觉人体 3D lifting**：输入现有 2D 关键点、置信度与短历史，输出 3D 关节/SMPL-X 参数；用 AMASS/mocap 姿态先验，真实录制序列作验证集。
3. **手部重建**：复用已有手部预训练网络，训练/微调到 Rove 的相机与常见胸前交互动作；用 InterHand2.6M、RenderIH 作公开预训练/评测，Rove 录制作域适应。
4. **面部 retarget**：训练或标定的是“52 个检测系数→目标模型表情权重”映射，不需要训练一个新的摄像头人脸网络；先用公开 ARKit-compatible rig 测出混合表达与冲突，再用目标模型细调。
5. **雷达融合**：等数据够后先做后融合基线（每关节视觉/雷达预测按置信度加权）；再尝试时空图网络 / cross-attention。保留单相机、单雷达和融合三组消融，证明雷达带来的净增益。

### 阶段 3：评测门槛与采购门槛

- 身体：MPJPE / PCK、骨长变化、关节越界率、左右翻转率。
- 手：3D 手关节误差、指尖抖动、握拳/张掌识别、手胸/手脸穿透次数。
- 腿：脚底离地误差、足滑距离、膝盖弯曲方向错误率、裙装遮挡下误分率。
- 脸：目标 blendshape 覆盖率、眨眼/张嘴/微笑响应延迟、无表情时权重漂移。
- 系统：端到端 p50/p95 延迟、低置信度恢复时间、摄像头丢失后的安全回退。
- **购买雷达的门槛**：在同一测试序列上，雷达融合相对视觉基线将被遮挡关节 3D 误差或足底接触错误率至少改善 20%，且不明显增加延迟；否则不进入硬件产品线。

## 7. 今日网页已落地内容与未完成边界

- 角色画面新增镜像开关，默认镜像并记住选择；它镜像显示中的角色，不改变摄像头采集或识别输入。上传 GLB 现在由同一个实时 Three.js 场景载入，不再只显示静态 `<model-viewer>`；检测到标准 ARKit 表情键时也会尝试按名称映射。
- 身体 3D 点位采用同一套图像坐标深度，手指重定向改用 MediaPipe 的 3D world landmarks 估掌面坐标系，再映射到目标模型指骨，降低纯 2D 带来的侧弯和扭转。
- 这不是深度学习在线再训练，也不是完整碰撞求解器。当前内置角色没有面部 morph targets，因此它仍不能产生真实面部形变；现在可以上传自带 ARKit 命名表情键和兼容 Mixamo 身体/手指骨架的 GLB 进行实时驱动尝试。VRM 专有表情和不同命名骨架尚未适配，实际上传模型仍需逐骨骼、逐表情验收。
- 尚未完成浏览器实时摄像头验证。镜像 UI 与手部姿态求解需在实际电脑上用“张掌、握拳、手放胸前、手放脸旁”四类动作检查左右侧、掌面方向和穿透。

## 8. GitHub CLI 不可用时的继续路径（2026-11-04）

- 本机 `gh auth login --web` 在申请设备码之前就因 `github.com` 连接失败退出；更换网络后复查仍无法解析域名、443 连通检查失败。因此 CLI 令牌认证尚未进行到需要用户输入验证码的阶段，不能生成或猜测授权码。
- Codex 已连接的 GitHub 工具可读公开仓库和文本源码，已成功读取 Ara 3D Gen 的面部、骨架和 package 文档。它不能返回二进制 GLB、模型权重或仓库压缩包。
- 后续源码研究、接口设计、网页改动可继续走 GitHub 连接器；要把角色资产真正放进项目，可通过能访问 GitHub 的浏览器下载生成器压缩包/导出的 GLB，再放入 `rove-site/models/`。收到文件后先检查许可、GLB 结构、骨骼和 morph targets，再设为页面默认资产。
- 当前已落地模块隔离：身体、手部、面部推理逐项捕获运行错误，单模块失败不再直接停止整帧；页面报告不可用模块。角色加载时向追踪面板发布可映射表情键数量，区分“检测到脸”与“模型脸确实能变形”。

## 9. 专项模型组合与许可筛选（2026-11-05）

- **网页即时路线**：继续使用 MediaPipe Pose / Hand / Face 三个独立任务。HandLandmarker 同时输出 21 个图像点、21 个米制 world landmarks 和手别；在本地浏览器可实时运行，是当前网页低延迟基线。推理调用阻塞主线程，后续可把三个任务移入 Worker，避免摄像头 UI 掉帧。
- **高精度离线/服务器手部候选**：HaMeR（CVPR 2024）或 WiLoR（CVPR 2025）从图像恢复 MANO 3D 手网格，适合作为第二阶段的手部质量对照/精细重建；它们不是可直接替换进网页的 JS 单文件模型，需要 Python/PyTorch、检测/裁剪、MANO 资产和显存/延迟评估。WiLoR 官方模型为 CC-BY-NC-ND，Rove 商业化产品不能默认使用；HaMeR 源码为 MIT，但权重、MANO 数据及依赖需逐项核实，不能仅凭代码许可证视作整套资产可商用。
- **脸部**：MediaPipe FaceLandmarker 继续输出面部 blendshape 信号；目标角色采用带 morph targets 的 rigged GLB。此处通常是“感知网络输出权重→目标模型形态键”的映射问题，无需另加一个面部生成模型。
- **统一融合契约**：各模块只输出时间戳、坐标系、关键点/形态权重、置信度与模块状态；融合层负责坐标归一、时间滤波、按置信度更新可见关节、缺失部位保留上一可靠姿势、限幅和角色重定向。任何模型单帧失效不得清空其余模块结果。
- GitHub 参考实现 `rana-jatin/avatar-stage` 采用 canonical humanoid roles、别名映射和“只驱动当前骨架确实具备的动作”的策略。本页已扩展 Mixamo、CC4、VRoid/J_Bip、Rigify 常见骨名归一，并在模型报告中列出身体关键骨段、30 个手指指节与表情键覆盖数；尚未导入完整第三方 retargeting 库。

参考：[MediaPipe Web Hand Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/web_js) · [HaMeR 论文](https://openaccess.thecvf.com/content/CVPR2024/papers/Pavlakos_Reconstructing_Hands_in_3D_with_Transformers_CVPR_2024_paper.pdf) · [HaMeR 代码与 MIT 许可](https://github.com/geopavlakos/hamer) · [WiLoR 论文](https://openaccess.thecvf.com/content/CVPR2025/papers/Potamias_WiLoR_End-to-end_3D_Hand_Localization_and_Reconstruction_in-the-wild_CVPR_2025_paper.pdf) · [WiLoR 权重许可与依赖](https://github.com/rolpotamias/WiLoR)

## 10. 角色与表情链路已落地（2026-11-05）

- **默认角色替换**：网页默认角色改为 `rove-site/models/rove-avatar-cc0.glb`（36.8 MB），源资产为 TalkingHead 示例 `mpfb.glb`（Blender + MPFB 生成，作者标注 CC0）。结构：67 关节、30 根手指骨、66 个唯一 morph target（ARKit 命名 + 14 个 viseme 口型）、8 个网格、7 张内嵌贴图、无内置动画。`MODEL_LICENSE.md` 已记录许可与已移除的非商业候选（RPM 的 brunette、AvatarSDK、VRoid 均为 NC）。
- **表情映射修复**：此前 `applyFace` 只在 `rove-motion` 事件里调用，所以没有摄像头时表情自检不会动；现在渲染循环每帧应用表情通道，并补充 `jawOpen`、`eyeBlinkLeft/Right`、`browInnerUp`、`eyeWide/Squint`、`cheekSquint`、`noseSneer`、`tongueOut` 等 ARKit 通道。结构报告显示 52 个 ARKit 通道、125 条网格 morph 绑定。
- **表情自检**：页面新增“表情自检”按钮，无需摄像头即可依次演示眨眼、张嘴、微笑、抬眉睁眼、皱眉，用于验收面部网格变形。
- **无头浏览器验证**：用 Chrome DevTools Protocol 打开 localhost 页面，DOM 报告“身体骨架 67、身体映射 19/19、指节 30/30、面部 52 通道”；合成 `rove-motion` 事件验证张嘴/微笑/眨眼均产生真实网格变形；合成身体关键点验证抬臂会带动肩肘腕。截图存于 `rove-site/docs/avatar-cc0-{idle,blink,smile}.png`。
- **仍有限制**：未在用户真实摄像头下实测；36.8 MB 角色本地加载约 0.2 s，远距离部署需压缩（Draco/meshopt、贴图降采样）；手指为 3 节骨而 MediaPipe 输出 4 点；viseme 口型通道已就绪但尚未接语音驱动。
